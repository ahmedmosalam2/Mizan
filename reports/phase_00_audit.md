# MIZAN — Phase 0 Repository Audit

**Date:** 2026-08-31
**Audit status:** Complete — remediation required before any official benchmark run
**Scope:** Repository state at commit `194bff5`; 67 tracked files; 3,069 lines across `mizan/` and `tests/`.

## Executive decision

The repository is a useful prototype of a Ramadan retail *benchmark harness*, not yet the required enterprise Application Under Test (AUT) plus reproducible scientific benchmark platform. The historical leaderboard, experiment log, and JSON result files must be treated as **invalid demonstration artifacts**: they were generated by adapters containing pre-populated outputs, token counts, costs, and successful deployment outcomes instead of real framework/runtime executions.

No historical score in `results/` or `reports/LEADERBOARD.md` is an official Mizan result.

## Current architecture

```text
CLI → runner → adapter → seven probe methods → evaluator → JSON/Markdown
                 │
                 ├─ SQLite service
                 ├─ local TF-IDF product search
                 ├─ regex PII redaction
                 └─ Python subprocess execution

Docker Compose defines PostgreSQL, Redis, RabbitMQ, Qdrant, MinIO,
OpenSearch, Prometheus, Jaeger, and Grafana, but the Python application
does not integrate with those services and Compose has no API or worker.
```

### Boundary assessment

| Required layer | Current state | Audit conclusion |
|---|---|---|
| Enterprise AUT | No API, workflow engine, six executable business agents, channel adapters, RBAC, or tenant context | Missing |
| Benchmark engine | Probe runner, adapter registry, evaluator, and configuration skeleton exist | Present but not scientifically valid |
| Evaluator | Rubric-based scorer exists | Scores declared fields rather than verified evidence; must be rewritten |
| Infrastructure | Docker service definitions and a partial PostgreSQL DDL exist | Defined but disconnected and internally inconsistent with SQLite runtime |

## Verified working pieces

These components execute locally against the small synthetic fixtures; this is **not** a claim of production readiness.

- SQLite can persist the current sample catalog, customers, consent events, and customer memory.
- The local TF-IDF store can retrieve from the fixture catalog.
- The PII engine detects and redacts the configured identifier, phone, and email patterns.
- The code executor can run a Python subprocess with a timeout.
- With temporary directories redirected into the workspace, the current suite passes: `11 passed in 2.50s`.

## Critical findings

### P0 — fabricated runtime evidence

`native`, `crewai`, `langgraph`, and `autogen` adapters build output objects directly. They populate successful status, task plans, deployment/fallback outcomes, token values, and costs in source code. `LangGraphAdapter.setup` and `AutoGenAdapter.setup` are empty; the CrewAI/LangGraph/AutoGen libraries are not used to execute agent graphs or conversations.

Impact: benchmark results, leaderboard order, latency, cost, safety, and reliability values are invalid. The evaluator largely awards points when fields are non-empty, so it cannot distinguish reported behavior from verified behavior.

Required fix: introduce one canonical execution contract and evidence trail, implement a real native runtime first, then map LangGraph, CrewAI, and AutoGen to the same task definitions. Store observable runtime/tool evidence before evaluation. Do not publish comparative scores until this is complete.

### P0 — missing AUT and security boundary

There is no business workflow that creates a company campaign, decomposes it into persisted atomic tasks, requests/awaits approval, deploys approved content, and analyzes actual campaign data. There is also no runtime authorization, authentication, company context propagation, or tenant isolation. The present agent profiles are prompts/configuration only.

Impact: the system cannot meet the six-agent, approval, consent, idempotency, or cross-company isolation requirements.

Required fix: implement the AUT independently of framework adapters, with a validated campaign state machine, permissioned tool gateway, tenant-scoped repositories, persistent approvals, and explicit `TEST`/`SANDBOX`/`REAL` execution modes.

### P0 — unsafe code execution claim

`CodeExecutor` writes arbitrary Python to a temporary file and starts it with the host interpreter. A timeout alone is not process isolation; code can import modules, read/write accessible files, and create child processes.

Impact: it must not be exposed as an analytics sandbox.

Required fix: replace it with an isolated execution backend (container/locked-down worker) or disable arbitrary code in non-test modes. Enforce resource, filesystem, network, import, and process controls; record execution provenance without retaining sensitive code/output.

### P1 — storage and infrastructure are disconnected

Runtime data uses a SQLite schema that does not match `scripts/init_db.sql`. PostgreSQL DDL lacks several required entities (roles, permissions, tool calls, evaluations, benchmark runs/results, metrics, incidents) and has incomplete tenant ownership. Redis, RabbitMQ, Qdrant, MinIO, and observability services have no application clients. Compose exposes placeholder credentials and contains no `api` or `worker` services.

Required fix: choose PostgreSQL as production source of truth; add migrations and tenant foreign keys; implement repositories; integrate only services actually used; move credentials to environment/secret references; add API/worker images and health checks.

### P1 — contracts and state are incomplete and duplicated

Pydantic core models are a good start, but they are duplicated by adapter dataclasses and do not define a single canonical `AgentRequest`, `AgentResponse`, `ToolRequest`, `ToolResponse`, `ApprovalDecision`, `CampaignResult`, `EvaluationResult`, or `BenchmarkResult` contract. `CampaignState.phase` is an unrestricted string, not a validated state machine.

Required fix: make the canonical Pydantic contracts the only cross-layer representation. Enforce legal campaign transitions and classify errors at the contract boundary.

### P1 — privacy and auditability are incomplete

The PII matcher is fixture-oriented. Raw PII can appear in runtime probe outputs, tool-call data, JSON results, and SQLite tables. Consent audit data is mutable, lacks company linkage, and is not an immutable ledger. Customers are handled with a KSA jurisdiction in paths that also process Egypt data.

Required fix: centralize redaction before logs, traces, prompts, vector writes, results, and reports; enforce consent at the tool gateway; append audit events with tenant/run/task context; test KSA and Egypt rules independently.

### P1 — data, task suite, and statistics are insufficient

The checked-in fixture set has 5 products and 5 customers, not the required 5,000+ product dataset plus campaigns, orders/conversions, channel metrics, policies, and bilingual market data. The seven broad probes are not versioned atomic tasks and have no controlled repeated-trial protocol, experiment registry, confidence intervals, or validated reduction analysis.

Required fix: create versioned atomic task manifests with deterministic fixture references, a synthetic-data generator that labels its output, experiment provenance, repeated runs, and statistics generated only from stored measurements.

## Contradictions and stale artifacts

- `README.md` claims “Zero Mocks” and real production services, while the adapters synthesize most benchmark behavior.
- The previous Phase 0 and Phase 1 reports declared success despite the unresolved fabricated adapters identified in `reports/problems/001_fabricated_adapters.md`.
- `configs/frameworks.yaml` marks adapters such as Agno as supported although no corresponding adapter exists; only four adapters register.
- `configs/evaluation.yaml` refers to a non-existent `mizan/scenarios/ramadan_retail/...` path; the repository uses `mizan/scenario/...`.
- `pyproject.toml` and `requirements.txt` duplicate and diverge on dependency declarations. Ruff is configured but unavailable in the inspected Python environment.
- `docker-compose.yml` defines more services than are used and exposes development credentials in the file.
- The existing result files and leaderboard are incompatible with the master prompt’s “no fake benchmark results” rule.

## Configuration and storage decisions

Keep one typed configuration loader with this precedence: explicit CLI arguments → environment variables/secrets → environment YAML → benchmark/task YAML defaults. YAML will describe tasks, benchmark suites, model policies, and non-secret environment endpoints; business behavior remains Python code.

- **PostgreSQL:** transactional AUT, audit, provenance, evaluation, and benchmark metadata.
- **Redis:** bounded session/cache/lock/checkpoint state only.
- **RabbitMQ:** durable asynchronous jobs, retries, and dead-letter queues.
- **Qdrant:** tenant-filtered product/document knowledge; never raw unredacted PII.
- **MinIO/S3:** artifacts and reports by immutable reference.
- **OpenTelemetry stack:** sanitized observable traces, logs, and metrics only.

## Phase 1 implementation order

1. Retire the probe-only result schema from the production path and preserve historical files only as explicitly invalid legacy artifacts.
2. Define canonical Pydantic contracts, error taxonomy, execution mode, tenant context, tool policy, and campaign state machine.
3. Add contract and transition tests before wiring external runtimes.
4. Build the native AUT workflow and tenant-scoped tool gateway.
5. Add real framework adapters one at a time, then evaluation, repeated-run experiments, and reporting.
